1. Project Title, Abstract, Problem Statement and Objectives

1.1 Title

WebMind — A Human-Like Computational Memory Engine for the Web Browser (a privacy-preserving, local-first browser extension that turns a user's browsing history into an associative, decaying, multi-modal memory that can be queried in natural language).

1.2 Abstract

Modern users consume large volumes of web content but retain very little of it. Browser history is a flat, reverse-chronological list keyed on exact URLs and titles; it offers no notion of importance, no forgetting, no association between related pages, and no ability to answer a question such as “what did I read about vector databases last week?”. WebMind reframes browsing history as a computational model of human memory. A Chrome (Manifest V3) extension passively captures each page, together with behavioural engagement signals (dwell time with focus-aware pausing, maximum scroll depth, revisit count, bookmark state) and page media (content images, videos). A local Node.js “sidecar” server converts page text and vision-model image captions into 768-dimensional embeddings using a locally hosted nomic-embed-text model, stores them in an on-device vector store (LanceDB), extracts concepts and named entities, and incrementally builds a knowledge graph of concepts, memories, domains, sessions, images and clusters (2,500+ nodes, 88,000+ edges in the current test corpus). Retrieval is hybrid: approximate-nearest-neighbour semantic search is fused with graph traversal (spreading activation over 2 hops) and re-ranked by a memory-strength score that combines engagement, an exponential Ebbinghaus-style decay term, revisit-based decay resistance, bookmark boosting and manual pinning. A large-language-model (Llama 3.2) then reconstructs a cited, natural-language answer from the retrieved fragments rather than returning raw links. All inference runs locally by default; an optional provider-abstraction layer allows the Llama and LLaVA models to be offloaded to a private AWS SageMaker endpoint (behind a single shared API key) while embeddings always remain local. The system is implemented in ~19,000 lines of code with 415 automated test cases across 18 test suites.

1.3 Problem Statement

The browser is the primary interface through which knowledge workers, researchers and students acquire information, yet the browser's own memory of that activity is impoverished:

  • No prioritisation. A page skimmed for two seconds and an article studied for twenty minutes are stored identically.
  • No forgetting. History grows without bound; stale, low-value pages compete equally with recent, important ones, degrading any ranking built on top of it.
  • No association. Two pages about the same topic, visited a month apart, have no relationship; recalling one does not surface the other.
  • No context. The fact that eight pages were part of one focused research session is lost.
  • Lexical, not semantic, recall. History search matches substrings of the title/URL; it fails for “that page with the dark database diagram” or paraphrased queries.
  • No synthesis. The user must re-open and re-read pages to reconstruct what they learned.
  • Privacy tax on the alternatives. Cloud “second brain” and retrieval-augmented-generation tools that do offer semantic recall typically upload the user's entire reading history to third-party servers.

Problem: Design and build a local-first system that continuously and passively converts a user's web browsing into a queryable, human-like memory — one that prioritises what mattered, forgets what did not, connects related material, preserves session context, supports multi-modal and natural-language recall, and synthesises cited answers — without any browsing data leaving the user's device.

1.4 Objectives

  1. O1 — Passive multi-modal capture. Capture page text, engagement signals (focus-aware dwell time, scroll depth, revisits, bookmarks) and page media without disrupting browsing.
  2. O2 — Local embedding and storage. Generate 768-d text embeddings on-device and store them with structured metadata in a hybrid SQLite + LanceDB + graph store.
  3. O3 — Associative knowledge graph. Extract concepts/entities, build a persistent concept–memory–domain–session graph with co-occurrence-weighted associations, and traverse it for recall within two hops.
  4. O4 — Human-memory dynamics. Implement an engagement score, an exponential decay function with revisit-based resistance, bookmark boosting and manual pinning, applied at query time.
  5. O5 — Contextual memory. Detect browsing sessions from temporal gaps and embedding similarity; preserve visit sequence for “before/after” queries.
  6. O6 — Multi-modal recall. Caption content images with a vision-language model and embed the captions into the same vector space as page text.
  7. O7 — Hybrid retrieval + reconstruction. Fuse semantic and associative retrieval, re-rank by memory strength, and use a local LLM to synthesise a cited answer with graceful search-only fallback.
  8. O8 — Autonomous organisation. Cluster memories with HDBSCAN, label clusters with an LLM, and expose the knowledge graph through an interactive visualiser.
  9. O9 — Privacy and portability. Keep all data and inference local by default; provide a clean provider abstraction for optional private-cloud model hosting and a full data-export path.
  10. O10 — Configurability and robustness. Expose all tunable coefficients through a validated configuration API, and degrade gracefully when any model backend is unavailable.

2.2 Research Gap

Across the literature, the following combination is not addressed by any single existing system:

  1. Cognitively-grounded ranking. Existing personal-search and second-brain tools rank by recency or raw embedding similarity. None combine a behavioural engagement score, an Ebbinghaus-style query-time decay term and revisit-based decay resistance with manual override (pin/bookmark) into a unified memory-strength function.
  2. Live associative index over personal browsing. GraphRAG-style graph indices exist for static document corpora; WebMind maintains an incrementally updated concept/memory/session graph over a continuously growing personal stream and fuses its traversal with vector search.
  3. Session and sequential context. Browser history and PIM tools discard the fact that a burst of pages formed one research session; WebMind reconstructs sessions from temporal gaps and inter-page embedding similarity and preserves visit order.
  4. Multi-modal recall without a cloud vision API. Image search over browsing normally requires uploading images to a hosted CLIP/vision service; WebMind captions images with a local vision-language model and embeds the captions into the shared local text space.
  5. Strict local-first privacy with an optional, clean cloud-offload seam. The provider-abstraction layer lets the two heavy models (LLM, VLM) move to a user-owned private endpoint independently, while the embedding model — the component that would otherwise see every page — is architecturally pinned to the device.

Gap statement: There is no open, local-first browser-integrated system that unifies behavioural engagement, human-memory decay dynamics, an incremental associative knowledge graph, session context, local multi-modal embedding and LLM-based cited reconstruction into a single privacy-preserving recall pipeline. WebMind targets exactly this intersection.

3. Proposed Methodology and System Architecture

3.1 Design Principles

  • Local-first: data and (by default) all inference stay on the device.
  • Passive & non-blocking: capture never delays page load; heavy work is asynchronous on the sidecar.
  • Hybrid storage: SQLite for structured metadata, LanceDB for vectors, an in-process graph (graphology) for associations.
  • Dual retrieval: embeddings for semantic recall, graph traversal for associative recall, fused and re-ranked.
  • Reconstructive output: return a synthesised, cited answer, not just links; degrade to search-only if the LLM is down.
  • Provider abstraction: callers ask for generateText() / generateImageCaption(); a single module decides local Ollama vs. private AWS endpoint per user setting.

3.3 Ingestion Methodology (per page visit)

  1. Capture. After a 5 s settle delay (and again on visibilitychange/beforeunload), the content script sends title, URL, first 10,000 chars of innerText, timestamp, {dwellTime, scrollDepth, revisitCount}, session context and de-duplicated media.
  2. Engagement score = 0.4 · min(dwell/300s, 1) + 0.3 · (scroll/100) + 0.3 · log(1+revisits)/log(101).
  3. Memory strength = (engagement · 0.4 + association_boost + revisit_boost) × (bookmarked ? 2.0 : 1.0), with revisit_boost = min(0.1 · log(1+unique_visit_days), 1).
  4. Session detection. New session if gap > 30 min or cosine similarity between consecutive page embeddings < 0.7; otherwise continue current session; sequence number incremented.
  5. Upsert. One memories row per URL; revisits merge metrics (accumulate dwell, max scroll) and skip re-embedding.
  6. Text embedding. nomic-embed-text, 768-d, 8k context, char-capped; stored in LanceDB with memory_id; failures enter a retry queue.
  7. Concept / entity extraction. natural library — word tokeniser + Porter stemmer + TF-IDF for topics; rule/gazetteer NER for PERSON / ORG / TECH / TOPIC with confidence 0.6–0.9; concepts below 0.6 dropped.
  8. Graph update. Add/merge concept nodes (occurrence count), add memory node, domain hub, session-sequence edge to previous memory, memory–concept links, and co-occurrence-weighted concept–concept associations (persisted when strength > 0.3).
  9. Image pipeline. For up to 6 captionable images: reuse an existing caption for the same URL if present, else call the VLM (local LLaVA or AWS); embed alt + caption with nomic-embed-text; add an image node linked to its memory; a consecutive-failure breaker stops hammering an unstable backend.

3.4 Retrieval & Reconstruction Methodology (per query)

  1. Query embedding (cached per query string; 55 s budget on CPU).
  2. Semantic recall. LanceDB ANN search, top-k (default 20).
  3. Associative expansion. Extract concepts of the top results; breadth-first graph traversal to 2 hops over edges with association strength ≥ 0.3; collect connected memories.
  4. Scoring. combined = ws·semantic + wa·associative (default 0.6 / 0.4); associative term carries a hop penalty (1.0 / 0.7 / 0.4 for 0 / 1 / 2 hops); each candidate's memory strength is decayed at query time by strength × e−r·days, where r = min(base_rate / (1 + 0.1·revisits), 0.005) and pinned memories use r = 0.
  5. Temporal filter. Natural-language time expressions in the query (“yesterday”, “last week”, “3 days ago”, weekday names) are parsed to a date window and applied, with fallback to all-time if empty.
  6. Reconstruction. Top memories (default 5) are formatted into a context block; a system instruction pins the model to the supplied snippets; Llama 3.2 produces a 2–3 sentence answer; citations (title, URL, relevance, excerpt) are attached. Per-stage timeouts (embed 55 s / retrieval 10 s / synthesis 10 s) guarantee a response; if the LLM/Ollama is unavailable the API returns ranked results in “search-only” mode.

3.5 Knowledge-Graph & Clustering Methodology

  • Graph: single undirected graphology graph, node types {concept, memory, domain, session, image, cluster}, edge types {concept_association, memory_concept_link, session_sequence, domain_membership, memory_image_link, cluster_membership, cross_cluster_link}. Persisted to JSON; auto-saved when dirty; reconciled against SQLite on startup (orphan purge + missing-node back-fill).
  • Clustering: memory embeddings are streamed to a Python HDBSCAN worker (hdbscan_cluster.py, min cluster size 3); each cluster's top concepts are sent to the LLM for a ≤5-word label; cross-cluster edges are added when centroid similarity > 0.5.
  • Visualiser: GET /graph serves a vis-network single-page app with Full / Journey / Domains / Topics layouts, time and site filters, a concept-frequency slider, type toggles, node inspector, and honest “subset view” reporting when the render is capped.

6.3 Observations that changed the design

  • Associative explosion. Aggressive TF-IDF concept extraction produces a very dense concept–association mesh; the graph view must render an honest “subset” and the retriever must cap hops and edge budgets. Concept-extraction thresholds are a future tuning target.
  • Single-thread contention. Local embedding during ingest blocks unrelated API calls; this motivated the caches, batched queries, request coalescing and, ultimately, the optional cloud offload for the two heavy models.
  • Chat models resist “history” framing. A system prompt that declares the snippets to be ground-truth history is required for reliable reconstruction on instruction-tuned endpoints.
  • Session rows were never written because the content script always supplies a session id; fixed with an idempotent upsert plus a startup back-fill from existing memories.

12. Suitability as a Potential Best Project

The identification of potential best projects is the prerogative of the review panel. For the panel's consideration, the following points summarise why WebMind is a strong candidate:

  • Clear novelty at a real intersection (§2.2): a cognitively-grounded, incrementally associative, local-first, multi-modal personal-memory retrieval pipeline that no single existing system provides.
  • Substantial, working implementation: ~19k LOC, 24-endpoint service, ~85% of the specified scope functional end-to-end, 415 automated tests, a live knowledge graph of ~2.5k nodes.
  • Engineering depth: hybrid storage (SQLite + LanceDB + graph), query-time decay maths, graph–vector fusion, an HDBSCAN subprocess, a provider-abstraction seam with independent per-model switches, per-stage timeouts, caches, request coalescing and graceful degradation — each backed by tests.
  • Privacy as a first-class design constraint: the embedding model, which would otherwise observe every page, is architecturally prevented from leaving the device even when cloud offload is enabled.
  • Publication-ready: a formal 30-requirement specification, a 1,496-line design document, a reproducible one-command setup, and (in this document) a drafted problem statement, literature survey, methodology, architecture and evaluation plan.
  • Demonstrable: an interactive graph visualiser and a scripted end-to-end demo make the contribution tangible in a review setting.

Remaining gaps (native CLIP, video-thumbnail embedding, at-rest encryption, 100k-scale archiving, formal evaluation study) are scoped, non-core, and planned for the final phase.
